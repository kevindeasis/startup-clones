# Build spec — Praxis clone ("Docketeer": AI agents that run a small law firm's admin, lawyer approves every step)

**Original:** Praxis (YC F26, launched 2026-10-15) — https://runpraxis.ai · YC page: https://www.ycombinator.com/companies/praxis
**Product (from public pages):** "AI agents that run law firm operations, from first inquiry to paid invoice. Agents do the work, lawyers approve." Four pillars on the YC page: **Win** (answer inquiries fast, screen them against the firm's rules, run a conflict check, draft an engagement letter for approval), **Onboard** (collect and verify client data and documents at upload, chase missing/outdated items automatically), **Run** (track tasks, follow up with clients and counterparties, give clients live progress through a portal), **Get paid** (send, track and chase invoices until paid). Target: small and mid-sized US law firms. Integrates with calendar, email, e-signature, billing and practice-management systems.
**Clone name:** `docketeer`. Single fictional firm ("Harbor & Vale LLP", business/employment law), self-hosted, no auth for staff. All data fictional. **No real email/e-sign/payments**: "sending" writes to an `outbox` table; e-signature is a typed name in the client portal; payment is a "Pay now" button that marks the invoice paid. Email, calendar and PMS integrations are simulated by the SQLite DB.

## The one rule that defines the product
**Nothing leaves the firm without lawyer approval.** Every agent-drafted outbound item (reply email, engagement letter, document request, chaser, status update, invoice, payment reminder) is created as a `pending` row in `approvals`. Approving it executes the side effect (outbox row, status change, letter file). Rejecting it records the reason, which is shown to the agent on the next draft for that matter. The approval queue is the home screen.

## Core flows (all required)

1. **Win — inquiry intake pipeline.** Page `/inbox` lists inquiries (seeded with 8 fictional inbound emails/web-form leads of varied quality; plus a form to add one: name, email, phone, subject, message, source `email|web_form|referral`). Button **Run intake** on an inquiry runs the pipeline and shows each step's result:
   a. **Extract** (LLM, structured output): practice_area (`business|employment|real_estate|ip|litigation|family|criminal|immigration|other`), matter_type (free text), summary (2 sentences), client_type (`individual|company`), parties (list of `{name, role: client|adverse|other}`), jurisdiction (US state or `unknown`), urgency (`low|normal|high`), estimated_value_usd (int or null), questions_for_client (≤3).
   b. **Screen** against `firm_rules` (seeded: accepted practice areas = business, employment, real_estate, ip; jurisdictions = NY, NJ, CT; no criminal/family/immigration; minimum matter value $5,000 for litigation; decline if adverse party is an existing client). Output `accept | decline | needs_lawyer` + reasons. Rules are deterministic code, not LLM; the LLM only extracts.
   c. **Conflict check** (deterministic): normalise each party name (lowercase, strip punctuation/`inc|llc|corp|ltd|co`, collapse whitespace) and compare with `clients`, `matters.adverse_parties_json` and `contacts` using `rapidfuzz.fuzz.token_set_ratio`; ≥ 85 = **hit**, 70–84 = **possible**. A hit against an existing client as adverse party, or an existing adverse party as new client, is a conflict → `needs_lawyer`. Store every match with score and which record it matched.
   d. **Draft reply** (LLM): accept → warm reply proposing a 20-min consult with 2 proposed times (next 3 business days from `settings.today`, 10:00/15:00), listing what to prepare; decline → polite decline with a referral line to the state bar lawyer-referral service (no legal advice); needs_lawyer → holding reply ("a partner will review within one business day"). → `approvals` row type `reply_email`.
   e. If `accept`: **draft engagement letter** (LLM fills `scope`, `fee_arrangement`, `initial_retainer_usd`, `exclusions` into the firm's Jinja2 letter template in `app/templates/letter.md.j2`; fixed clauses are template text, not LLM text) → `approvals` row type `engagement_letter`, with a Markdown preview and, on approval, a `.docx` rendered with **python-docx** to `data/letters/<matter_id>.docx` plus the `.md`. Approval also creates the `client` (if new) and the `matter` in stage `engagement_sent`.
   The pipeline result (all steps + the approvals created) is stored on `inquiries.pipeline_json` and shown inline. Re-running is allowed and replaces it.

2. **Approval queue.** Page `/` (home): counters (pending approvals, new inquiries, matters by stage, documents outstanding, AR outstanding / overdue) and the list of pending approvals grouped by type, each with: matter/inquiry, agent's draft (editable textarea), agent's rationale, buttons **Approve**, **Save edits & approve**, **Reject** (reason required). Executing an approval: `reply_email|document_request|chaser|status_update|invoice_email|payment_reminder` → insert into `outbox` (to, subject, body, sent_at) and update the related row; `engagement_letter` → render docx/md, create client+matter, outbox row with the letter attached (path). Page `/outbox` lists everything "sent". Page `/activity` lists `agent_runs` (agent, matter, step, mode mock/live, model, input/output tokens, duration, created_at) with expandable prompt/response.

3. **Onboard — document collection and verification.** When the client **signs** the engagement letter in the portal (typed full name + checkbox; stores `signed_at`, `signed_name`), the matter moves to `onboarding` and the agent builds a **document checklist** from `checklist_templates` (by practice area, e.g. employment: government ID, employment agreement, termination letter, pay stubs (last 3), any written complaints; business: formation docs, cap table, the contract at issue, correspondence) **plus** up to 2 LLM-suggested extra items derived from the intake summary (each with a one-line reason). → `matter_documents` rows with status `requested`. A `document_request` approval is drafted (email listing the items and the portal link). Client uploads files in the portal (accept `.pdf`, `.txt`, `.md`, `.png`, `.jpg`; max 10 MB). **Verification** (LLM, structured output) runs on upload: text is extracted with **pypdf** (PDF) or read directly (txt/md); images get no OCR — pass only filename and the client's typed description. Output: `doc_type_detected`, `matches_requested` (bool), `names_found`, `dates_found`, `expiry_date` (or null), `issues` (list), `verdict: verified | mismatch | expired | unreadable | needs_lawyer`, `explanation`. Deterministic post-checks: expiry_date < today → `expired`; names_found none fuzzy-matching the client name (token_set_ratio ≥ 80) when the doc type is an ID → `mismatch`. Status is written to `matter_documents` and shown to the client ("Received, verified" / "We need a clearer copy: …"). **Chasers:** `POST /agents/run-daily` (button "Run daily agents" in the header, and callable from tests) finds documents still `requested|mismatch|expired|unreadable` for ≥ `CHASE_AFTER_DAYS` (default 3) since last request/chase and drafts one `chaser` approval per matter (escalating tone: 1st friendly, 2nd direct, 3rd flags that the matter is paused). Time is controlled by `settings.today` (ISO date) which the header **"Advance day +1 / +7"** buttons move, so the whole lifecycle can be demoed in minutes.

4. **Run — matter tracking and client portal.** `/matters` lists matters (client, practice area, stage `intake → engagement_sent → onboarding → active → closed`, next action, portal link). `/matters/{id}`: timeline (every outbox item, approval, document event, stage change), **tasks** (title, owner `lawyer|client|agent|counterparty`, due date, status `open|done|blocked`; add/complete inline), notes, documents, invoices. When all checklist docs are `verified`, the agent proposes a `status_update` approval ("onboarding complete, here's what happens next") and the matter moves to `active`. **Run daily agents** also drafts a `chaser` for each `open` task owned by `client|counterparty` that is overdue by ≥ 2 days (one email per matter, grouping tasks; counterparties get a neutral, professional tone, never legal threats). **Client portal** `/portal/{token}` (unguessable `secrets.token_urlsafe(16)` per matter, no login): firm header, matter status bar, "What we need from you" (document checklist with upload forms + task list for the client), engagement letter view + **Sign**, invoices with **Pay now**, and a read-only "Recent updates" list from the outbox. The portal never shows internal notes, conflict-check data or agent rationale.

5. **Get paid — invoicing and reminders.** `/matters/{id}` has **time entries** (date, minutes, description, rate from `settings.default_rate_usd` 350; add inline; seed a few on active matters). Button **Generate invoice** → the agent (LLM) rewrites the raw entry descriptions into client-friendly narrative lines (keeps minutes/amounts unchanged, deterministic totals computed in code) and drafts the cover email → one `invoice` row (number `HV-YYYY-NNN`, status `draft`, due = issue + `INVOICE_NET_DAYS` 30) and one `invoice_email` approval. Approve → invoice `sent`, outbox row, visible in the portal. **Run daily agents**: for `sent` invoices past due → `payment_reminder` approvals with escalating tone at +7 (friendly), +14 (firm), +30 days (final notice, mentions pausing work; no threats of legal action), at most one per invoice per stage. Portal **Pay now** → `paid`, `paid_at`. `/billing`: AR table (invoice, client, amount, status, days overdue) and totals.

## Stack
Python 3.11+, **FastAPI + Uvicorn**, SQLite via stdlib `sqlite3` (no ORM), **Jinja2** templates + vanilla JS/CSS (no build step), pydantic v2. Dependencies (all verified on PyPI 2026-11-16): `anthropic` (2.x), `fastapi`, `uvicorn[standard]`, `pydantic`, `jinja2`, `python-multipart` (uploads/forms), `python-dotenv`, `rapidfuzz` (conflict check), `pypdf` (PDF text), `python-docx` (engagement letter .docx), `markdown` (render letter/email previews), `pytest` + `httpx` (tests with FastAPI `TestClient`). Pin with `>=` minimums in `requirements.txt`.

### LLM layer (`app/llm.py`) — Anthropic SDK directly, no LangChain
- Client: `anthropic.Anthropic()` (reads `ANTHROPIC_API_KEY`). Model from `ANTHROPIC_MODEL`, default **`claude-opus-5-5`** (cheaper option `claude-sonnet-5-5` documented in `.env.example`). Do not append date suffixes to model IDs.
- **Structured outputs** for every extraction/verification/drafting step: `client.messages.parse(model=..., max_tokens=4096, system=..., messages=[...], output_format=<pydantic model>)` and read `response.parsed_output`. Do **not** use forced `tool_choice` (`any`/`tool`) — current models reject it — and do not use assistant prefill. Do not set `temperature`. Omit the `thinking` parameter; set `output_config={"effort": "low"}` for extraction/verification and `"medium"` for drafting.
- One function per agent step, each returning a pydantic model: `extract_inquiry`, `draft_reply`, `draft_engagement_terms`, `suggest_checklist_extras`, `verify_document`, `draft_document_request`, `draft_chaser`, `draft_status_update`, `draft_invoice_narrative`, `draft_payment_reminder`. Each writes an `agent_runs` row (mode, model, input/output tokens from `response.usage`, duration, prompt and raw output).
- **Mock mode** (required; the sandbox has no key): `MOCK_LLM=1` or no `ANTHROPIC_API_KEY` → `MockLLM` returns deterministic, plausible outputs built from the inputs with keyword rules (e.g. "fired|terminated|wrongful|harass" → employment; "contract|vendor|breach|shareholder" → business; "arrested|DUI" → criminal; "divorce|custody" → family; "visa|green card" → immigration; party names pulled from capitalised two-word sequences and "vs|against|my employer <Name>" patterns; documents: txt containing "EXPIRES: YYYY-MM-DD" in the past → expired, an ID without the client's name → mismatch). Mock output must be good enough that the whole demo and all tests pass without a key. `/health` reports `{"mode": "mock"|"live", "model": ...}`.
- System prompt (shared preamble in `app/prompts.py`): the agent is the operations assistant of Harbor & Vale LLP; it never gives legal advice, never promises outcomes, never threatens legal action, writes in plain professional English, keeps emails under 180 words, uses the firm profile (name, address, practice areas, consult policy) and the lawyer's past rejection reasons for this matter (passed in) as instructions.

## Data model (SQLite, `app/schema.sql`, created and seeded on first start; `data/docketeer.db`, path from `DATABASE_PATH`)
- `settings(key, value)` — `today` (ISO date, defaults to real today on first seed), `default_rate_usd`, `firm_json` (name, address, phone, email, practice_areas, consult_policy, bar_referral_line).
- `firm_rules(id, rule_type 'accept_area'|'accept_jurisdiction'|'decline_area'|'min_value'|'custom', value, note)`.
- `clients(id, name, type, email, phone, address, created_at)`; `contacts(id, name, kind 'adverse'|'counsel'|'other', matter_id, note)`.
- `inquiries(id, received_at, source, name, email, phone, subject, message, status 'new'|'processed'|'accepted'|'declined'|'needs_lawyer'|'converted', pipeline_json, created_at)`.
- `matters(id, client_id, inquiry_id, title, practice_area, matter_type, summary, adverse_parties_json, stage, portal_token, lawyer_name, created_at, updated_at)`.
- `engagement_letters(id, matter_id, terms_json, markdown, docx_path, status 'draft'|'sent'|'signed', sent_at, signed_at, signed_name)`.
- `approvals(id, type, matter_id, inquiry_id, title, draft_text, subject, to_email, rationale, payload_json, status 'pending'|'approved'|'rejected', reject_reason, created_at, decided_at)`.
- `outbox(id, matter_id, to_email, subject, body, attachment_path, kind, sent_at)`.
- `checklist_templates(id, practice_area, item, description, required)`.
- `matter_documents(id, matter_id, item, description, status 'requested'|'received'|'verified'|'mismatch'|'expired'|'unreadable'|'needs_lawyer', file_path, original_name, client_note, verification_json, requested_at, last_chased_at, chase_count, uploaded_at, verified_at)`.
- `tasks(id, matter_id, title, owner, due_date, status, created_at, done_at, last_chased_at)`.
- `time_entries(id, matter_id, entry_date, minutes, description, rate_usd, invoice_id)`.
- `invoices(id, matter_id, number, status 'draft'|'sent'|'paid'|'void', issue_date, due_date, subtotal_usd, lines_json, cover_email, reminder_stage 0..3, sent_at, paid_at)`.
- `agent_runs(id, agent, matter_id, inquiry_id, mode, model, input_tokens, output_tokens, duration_ms, prompt, output, created_at)`.
- `events(id, matter_id, kind, text, created_at)` — the timeline.
Seed: firm profile, rules, 4 checklist templates, 5 existing clients (incl. "Northwind Logistics LLC" and "Dana Whitfield"), 3 existing matters in various stages with adverse parties (incl. "Crestline Holdings Inc."), 8 inquiries — among them one whose adverse party is Northwind Logistics (conflict), one criminal (decline), one out-of-state family matter (decline), one strong employment lead, one business contract lead, one vague message (needs_lawyer), one with "Crestline Holdings" as the prospective client (conflict). One active matter has time entries and one has a `sent` invoice 20 days overdue.

## Screens / endpoints
Pages: `/`, `/inbox`, `/inbox/{id}`, `/matters`, `/matters/{id}`, `/outbox`, `/activity`, `/billing`, `/portal/{token}`, `/health`.
JSON/form API (used by the pages' JS and by tests): `POST /api/inquiries`, `POST /api/inquiries/{id}/run`, `GET /api/approvals?status=pending`, `POST /api/approvals/{id}/approve` (optional edited `draft_text`), `POST /api/approvals/{id}/reject` (`reason`), `POST /api/matters/{id}/tasks`, `POST /api/tasks/{id}/done`, `POST /api/matters/{id}/time`, `POST /api/matters/{id}/invoice`, `POST /api/portal/{token}/sign`, `POST /api/portal/{token}/upload` (multipart: `document_id`, `file`, `note`), `POST /api/portal/{token}/pay/{invoice_id}`, `POST /agents/run-daily`, `POST /api/settings/advance?days=N`, `GET /api/matters/{id}` (JSON snapshot incl. documents, tasks, invoices, stage).

## Env vars (`.env.example`)
`ANTHROPIC_API_KEY=` (blank → mock), `ANTHROPIC_MODEL=claude-opus-5-5`, `MOCK_LLM=` (set `1` to force mock), `DATABASE_PATH=data/docketeer.db`, `UPLOAD_DIR=data/uploads`, `CHASE_AFTER_DAYS=3`, `INVOICE_NET_DAYS=30`, `PORT=8000`.

## Skip
Staff auth/roles, billing of the SaaS itself, real email/calendar/e-sign/payment/PMS integrations, OCR, multi-firm tenancy, PDF generation of invoices (HTML view is enough), trust accounting, real legal templates (the letter is a plainly-labelled fictional sample).

## Acceptance checks (the build must pass all; write them as pytest tests where marked T)
1. `pip install -r requirements.txt` succeeds on Python 3.11; `uvicorn app.main:app` boots with **no** API key; `/health` returns 200 with `mode: mock`. **T**
2. All pages above return 200 (portal via a seeded token). **T**
3. Intake on the strong employment lead → `accept`, no conflict, creates `reply_email` + `engagement_letter` approvals; the reply mentions two consult times. **T**
4. Intake on the inquiry adverse to Northwind Logistics → conflict hit (score ≥ 85 against client "Northwind Logistics LLC"), result `needs_lawyer`, only a holding `reply_email` approval, no letter. **T**
5. Intake on the criminal inquiry → `decline` with the rule named in reasons; the reply contains the bar-referral line and no legal advice. **T**
6. Approving the engagement letter creates the client and matter (stage `engagement_sent`), an outbox row, and a `.docx` file that `python-docx` can reopen; rejecting an approval with a reason stores it and a re-run of intake passes the reason into the next draft (visible in `agent_runs.prompt`). **T**
7. Portal sign → stage `onboarding`, checklist rows created (template items + ≤2 extras), one `document_request` approval. **T**
8. Uploading a `.txt` "ID" containing a different name → `mismatch`; uploading one with the client's name and a future expiry → `verified`; one with `EXPIRES:` in the past → `expired`. When all required docs are verified → `status_update` approval and stage `active` after approval. **T**
9. Advance 4 days + run daily agents → exactly one `chaser` approval per matter with outstanding documents; run again without advancing → no duplicate. **T**
10. Generate invoice on the matter with time entries → invoice `draft` with correct subtotal (sum minutes/60 × rate, rounded to cents) and an `invoice_email` approval; approve → `sent`, visible in portal; advance 8 days → `payment_reminder` stage 1; +7 more → stage 2; no duplicate per stage; Pay now → `paid`. **T**
11. Nothing is ever written to `outbox` without an approved `approvals` row (assert in tests by counting). **T**
12. `.gitignore` excludes `.venv/`, `__pycache__/`, `data/`, `.env`; no secrets in the repo; `README.md` is complete per the build instructions.
