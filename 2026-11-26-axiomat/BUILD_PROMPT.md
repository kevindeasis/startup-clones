# SPEC — Axiomat clone ("Proven")

Date: 2026-11-26. Original company: **Axiomat** (YC F26) — https://www.axiomat.com — launch post: https://www.ycombinator.com/launches/X3M-axiomat-agents-that-cannot-hallucinate

## What the product does

Axiomat is a data layer that lets AI agents answer questions about a company's business data **without hallucinating**. The company's business rules are turned into formal definitions; when an agent writes a query, Axiomat proves (in Lean) that the query matches the definition. "If we can't prove it, the query doesn't run." The agent retries until it has a proven answer or reports that it could not find one. Before answering, the user is shown how the question was understood, restated in unambiguous English **generated by code, not by the AI**.

This clone, called **Proven**, keeps the product shape but replaces the Lean proof assistant with a deterministic **semantic-layer verifier**: the LLM only produces a structured *interpretation* of the question; code compiles that interpretation into SQL from a rules file, code produces the English restatement, and a verifier (AST checks with sqlglot + data invariants run on DuckDB) must pass before any result is shown. Unverified queries never run against the user-visible path.

## Core user flows (implement all)

1. **Ask a question** — user types a natural-language question (e.g. "What was revenue by month in 2026?"). The app returns: the English restatement of how the question was interpreted, a verification certificate (list of checks, all passed), the SQL that ran, and the result table. A row of example-question chips is shown.
2. **See the retry loop** — when an interpretation fails verification, the app feeds the exact failure back to the LLM and retries (max 3 attempts). The UI shows an "attempts" log: each attempt, what failed, and why. If every attempt fails, the app answers "I couldn't find a proven answer" with the reasons, and shows **no numbers**.
3. **Browse the business rules** — a Rules page/panel listing every metric (name, plain-English definition, canonical SQL expression, mandatory filters), every dimension, and every data invariant, read from `rules.yaml`.
4. **Inspect the data schema** — a Schema panel listing tables/columns of the sample database and which ones are allowed for querying.
5. **Verify a raw SQL query** (the "agent integration" surface) — `POST /api/verify` takes arbitrary SQL + the metric it claims to compute and returns pass/fail with reasons, using the same verifier. The UI has a small "Verify SQL" tab for this.

## Sample dataset (`data/seed.sql`)

A small B2B SaaS dataset with deliberate traps that make naive queries wrong:

- `accounts(account_id, name, plan, status, is_trial, created_at, country)` — ~60 rows; ~10 are `is_trial = true`; some `status = 'churned'`.
- `subscriptions(subscription_id, account_id, plan, mrr, started_at, ended_at)` — one account can have several rows over time; only rows with `ended_at IS NULL` are active.
- `invoices(invoice_id, account_id, issued_at, total)`; `invoice_lines(line_id, invoice_id, description, amount)` — joining invoices to lines and summing `invoices.total` double counts (the trap).
- `payments(payment_id, invoice_id, paid_at, amount, status)` — `status IN ('succeeded','refunded','failed')`; revenue counts only `succeeded` minus `refunded`.

Dates span 2025-01 to 2026-11. Generate deterministic data in the SQL file (no random at runtime).

## Semantic layer (`rules.yaml`)

```yaml
tables:               # allowed tables and columns (anything else is rejected)
  accounts: [account_id, name, plan, status, is_trial, created_at, country]
  ...
dimensions:           # things you may GROUP BY / filter on
  - {name: month, sql: "date_trunc('month', {date_col})", kind: time}
  - {name: plan, table: accounts, column: plan}
  - {name: country, table: accounts, column: country}
  - {name: payment_status, table: payments, column: status}
metrics:
  - name: revenue
    english: "sum of succeeded payment amounts minus refunded amounts, by payment date"
    sql: "SUM(CASE WHEN payments.status = 'succeeded' THEN payments.amount WHEN payments.status = 'refunded' THEN -payments.amount ELSE 0 END)"
    base: payments            # FROM table
    joins: [invoices ON payments.invoice_id = invoices.invoice_id, accounts ON invoices.account_id = accounts.account_id]
    date_column: payments.paid_at
    required_predicates: ["payments.status IN ('succeeded','refunded')"]
    forbidden_tables: [invoice_lines]      # prevents the double-count trap
    invariants:
      - name: revenue_not_above_gross
        check: "({query_total}) <= (SELECT SUM(amount) FROM payments WHERE status='succeeded')"
  - name: customers       # paying, non-trial, non-churned accounts
    sql: "COUNT(DISTINCT accounts.account_id)"
    base: accounts
    required_predicates: ["accounts.is_trial = false", "accounts.status <> 'churned'"]
    invariants: [customers_not_above_accounts]
  - name: active_subscriptions   (subscriptions.ended_at IS NULL)
  - name: mrr                    (SUM(subscriptions.mrr) over active subscriptions)
  - name: trial_accounts         (COUNT where is_trial = true)
  - name: churned_customers
  - name: refunds                (SUM(amount) where status='refunded')
```
Implement at least these 7 metrics, 4 dimensions and 4 invariants. The exact YAML shape is up to the builder but it must be data, not code.

## LLM pipeline

**Interpretation schema (pydantic):**
```python
class Interpretation(BaseModel):
    metric: str                      # must be a metric name from rules.yaml
    group_by: list[str] = []         # dimension names
    filters: list[Filter] = []       # Filter(dimension: str, op: Literal['=', '!=', 'in'], value: str | list[str])
    time_range: TimeRange | None     # TimeRange(start: date, end: date)  (inclusive start, exclusive end)
    cannot_answer: str | None        # set when the question is outside the rules; nothing else is filled
```
**Prompt**: system prompt lists the metrics (name + english), dimensions, and allowed filter values; the user message is the question plus, on retries, the verifier's failure list. Use `client.messages.parse(model=..., max_tokens=2048, system=..., messages=[...], output_format=Interpretation)` from the official SDK (structured outputs). Model from `ANTHROPIC_MODEL`, default `claude-opus-5-5`. Thinking left at the API default (do not send `thinking` or `temperature`).

**Compiler (code only, `app/compiler.py`)**: Interpretation → SQL via sqlglot expression builders (or careful string templates parsed through sqlglot). Always injects the metric's `required_predicates`, joins, `date_column` for time filters, and dimension expressions. Also returns the **English restatement** built from templates, e.g. *"Count of distinct accounts that are not trials and not churned, grouped by plan, where country = 'CA', created between 2026-01-01 and 2026-07-01."* No LLM involvement.

**Verifier (`app/verifier.py`)**, run on the compiled SQL (and on raw SQL in flow 5). Each check returns `{name, passed, detail}`:
1. `parses` — sqlglot parses it as DuckDB SQL; exactly one SELECT statement, read-only (no DDL/DML).
2. `allowed_tables_columns` — every table/column referenced exists in `rules.yaml.tables`; the metric's `forbidden_tables` are absent.
3. `metric_expression_matches` — the aggregate expression in the SELECT list is AST-equal (after `sqlglot.optimizer.normalize`/canonicalize and qualification) to the metric's canonical `sql`.
4. `required_predicates_present` — each required predicate (parsed to AST) appears in the WHERE conjunction.
5. `group_by_consistent` — every non-aggregate SELECT column is in GROUP BY and is a known dimension expression.
6. `invariants_hold` — run each of the metric's invariant SQL checks on DuckDB with the candidate query's total substituted; all must return true.
7. `executes` — query runs with `LIMIT 1000` in a read-only connection within 5 s.
A result is "proven" only if all checks pass. The attempts log records every failed check with its detail string, which is what gets fed back to the LLM.

**Mock mode** (`PROVEN_MOCK=1` or no `ANTHROPIC_API_KEY`): a deterministic keyword-based interpreter (`app/mock_llm.py`) maps questions to Interpretations (metric synonyms, month/plan/country detection, year/quarter parsing). It must handle all example questions. To demonstrate the retry loop in mock mode, the question containing the phrase "including trials" produces a first interpretation with filter `is_trial = true`-style override that fails `required_predicates_present`, and the mock's second attempt corrects it. The UI shows a visible "MOCK MODE" badge.
